[![Meta](https://github.com/collective/collective.instancebehavior/actions/workflows/meta.yml/badge.svg)](https://github.com/collective/collective.instancebehavior/actions/workflows/meta.yml)

## Problem and Motivation

Behaviors, provided by the `plone.behavior` package, provide a very useful way of extending the functionality of a Dexterity content type.
Unfortunately, the fact that a content type's behaviors are stored in its factory contents information (FTI) inside the portal_types tool, means that they are class (or type) specific, and not instance specific.
This means that behaviors can only be enabled globally, in other words only for all the instances of a specific type.

To enable per instance behaviors, we need a way to store those behaviors on the instance.
We use annotations for this purpose.

Additionally, we provide our own `IBehaviorAssignable` adapter that overrides the default one.
It does not only look for an object's FTI registered annotations, but also look for the behaviors stored in the current instance's annotations.

Also helper functions are implemented which can be used to dynamically assign behaviors and interfaces on dexterity content objects.


## Compatibility

Version 0.6 supports Plone 6.1 and 6.2, on Python 3.10 to 3.13.

For older Plone versions and Python 2.7, use collective.instancebehavior 0.5.


## Installation

Depend your plone addon on `collective.instancebehavior`.


## Enable behaviors and interfaces

Note: the targeted object must implement `collective.instancebehavior.IInstanceBehaviorAssignableContent`.

```python
>>> from plone.app.event.dx.interfaces import IDXEvent
>>> enable_behaviors(
...     obj,
...     ['plone.app.event.dx.behaviors.IEventBasic'],
...     [IDXEvent]
... )
```


## Disable behaviors and interfaces

```python
>>> from plone.app.event.dx.interfaces import IDXEvent
>>> disable_behaviors(
...     obj,
...     ['plone.app.event.dx.behaviors.IEventBasic'],
...     [IDXEvent]
... )
```


## Caching

In some cases (ex: tests), you may need to clear Dexterity assignable cache after enabling or disabling instance behaviors.

```python
>>> from plone.dexterity.content import ASSIGNABLE_CACHE_KEY
>>> delattr(request, ASSIGNABLE_CACHE_KEY)
```

# Development

Requires [uv](https://docs.astral.sh/uv/). This installs the package with Plone 6.2.3 in `.venv` (use `PLONE_VERSION=6.1.6 make install` for another version) and the prek git hook. Plone is not a dependency of the package: the Makefile adds Products.CMFPlone and plone.app.contenttypes for the development instance.

```shell
make install
make start          # Plone on http://localhost:8080 (admin / admin)
make console        # Python console with the Zope application as `app`
```

## Tests

Tests run through tox, as the CI does:

```shell
make test                                   # Plone 6.2.3
uvx --with tox-uv tox -e py312-plone61      # one Plone / Python combination
make test-all                               # lint, every combination, dependencies
```

Without tox:

```shell
.venv/bin/zope-testrunner --all --test-path=src -s collective.instancebehavior
```

## Lint

```shell
make check          # format then lint (pyupgrade, isort, black, flake8...)
```

`.editorconfig`, `.flake8`, `.gitignore`, `.pre-commit-config.yaml`, `tox.ini`,
`.github/` and the tool sections of `pyproject.toml` are generated by
[plone.meta](https://github.com/plone/meta): change `.meta.toml`, then run
`uvx --from plone.meta config-package --no-commit --branch current .`.
